linux项目复现大纲

何涛 Lv1

明白。这次我们把学习计划正式确定下来，之后不再随意改变项目的功能或学习主线。

你的两个要求非常明确：

  1. 开发板和 SDK 都要等到第 11 天才能拿到。 前 10 天完全依靠 Windows + VS Code + VMware Ubuntu。
  2. 保留原项目的所有现有功能。 我们的任务是学习、理解、移植和适配，而不是删减功能、替换项目或重新设计一套简化系统。

Linux 应用开发 + RV1126B 原项目移植：最终 15 天计划

Day 1～10

无板阶段：打基础、吃透源码、准备移植

10 天

C++ 基础、Linux 多线程、网络通信、原项目各个核心模块、编译系统、移植分析和测试方案。

Day 11～15

有板阶段：SDK、双摄、原项目移植与测试

5 天

RV1126B 环境、交叉编译、SC530AI 摄像头、MPP、RKNN、多模型推理、拼图推流和功能回归。

一、先把“不改变原项目功能”明确下来

我重新核对了你上传的源码。原项目真正包含的核心功能如下：

原项目功能 我们的移植要求
1～6 路可配置视频输入 保留，不能直接固定成两路
本地视频 / RTSP 输入 保留原有输入方式
FFmpeg + MPP 解码 保留解码能力，允许适配 RV1126B SDK
人员、头盔、打电话三个模型推理 三个现有模型均需保留
多模型检测结果融合 保留融合逻辑
OpenCV 视频缩放、拼图、检测框绘制 保留
MPP 视频编码、RTMP 推流 保留
多线程调度、队列与运行监控 保留
命令行、环境变量等运行配置 保留原有配置方式

这些要求来自实际源码中的输入数量限制、模型创建、推理调度、画面处理和推流配置。

这里有一个重要区别：源码中虽然存在疲劳检测相关的数据结构和模型文件，但当前 main.cpp 实际初始化的是人员、头盔和打电话三个模型。因此，我们保留现有的三模型运行行为，不擅自增加第四个推理任务。

两颗 SC530AI 摄像头的接入，属于平台移植所需的输入适配，不是替换整个视频系统。原来的本地视频、RTSP、多模型检测、拼图和 RTMP 输出仍然保留。

我们的目标是：

原项目功能不减少、对外行为尽量一致，只修改平台兼容、驱动接口、库链接和必要的资源管理代码。

此外，原始源码包含禁止未经授权创建衍生作品的许可声明。在实际修改移植代码前，需要确认你或项目提供方已获得相应授权。学习、分析与独立练习可以先进行。

二、Day 1～10：没有开发板时，每天具体做什么？

这一阶段不依赖 SDK，所有编程练习都在 Ubuntu 虚拟机中完成，并且放在单独的 linux_practice 目录下。

原项目代码暂时只阅读、分析和记录，不做功能性修改。

第 1～3 天：补强 C++ 基础，理解项目入口

天数 每天具体学习任务 必须完成的成果
Day 1：环境和 C++ 入门巩固 ① Ubuntu、GCC、GDB、CMake 环境检查；② 学习编译、汇编、链接；③ 复习引用、const、指针；④ 阅读项目目录和 CMakeLists.txt；⑤ 用 GDB 调试 C++ 程序 环境检查报告、C++ 小程序、依赖清单
Day 2：STL 和内存管理 ① 学习 vector、string、map、queue；② 学习 new/delete、unique_ptr、shared_ptr、RAII；③ 编写多路视频配置管理 Demo；④ 阅读 main.cpp 中容器和对象创建代码；⑤ 学习对象生命周期 stream_config.cpp、内存管理笔记
Day 3：Linux 进程与多线程 ① 学习进程和线程区别；② 学习 std::thread、join、atomic；③ 编写 3 个工作线程的程序；④ 阅读 main.cpp 的 inference_thread、readerThread、app_stop；⑤ 画出原程序线程生命周期 thread_demo.cpp、原项目线程关系图

第 3 天验收： 能解释原项目为什么创建多个线程，各线程负责什么，以及应用程序退出时怎样协调资源释放。

第 4～6 天：并发、网络和视频输入

天数 每天具体学习任务 必须完成的成果
Day 4：线程同步与线程池 ① 学习 mutex、lock_guard、unique_lock；② 学习 condition_variable；③ 编写生产者消费者 Demo；④ 阅读 ThreadPool.hpp 和 m_buffer.hpp；⑤ 分析共享帧缓存的加锁逻辑 producer_consumer.cpp、线程同步流程图
Day 5：Linux I/O 和网络通信 ① 学习文件描述符、open/read/write/close；② 学习 TCP/UDP、Socket；③ 编写 TCP 客户端和服务端；④ 理解 RTSP 与 RTMP 的用途；⑤ 复习 errno 和阻塞 I/O TCP 通信 Demo、Linux I/O 笔记
Day 6：原项目视频读取与解码 ① 阅读 stream_loader.cpp 和 stream_loader.h；② 阅读 mpp_decoder.cpp；③ 分析 FFmpeg 视频读取与 MPP 解码的关系；④ 理解 AVPacket、NV12、帧缓存、stride；⑤ 画出视频输入到缓存的完整数据流 视频解码数据流图、接口与数据结构说明

到第 6 天时，你需要能够独立解释：

为什么原项目使用 FFmpeg 读取视频后，还需要通过 MPP 解码？一帧图像是怎样存入共享缓冲区的？如何避免读取线程与处理线程之间发生数据竞争？

第 7～10 天：理解原有全部功能，准备上板移植

天数 每天具体学习任务 必须完成的成果
Day 7：多模型推理模块 ① 阅读 rknnPool.hpp、postprocess.cpp；② 阅读 inferenceScheduler()；③ 理解三个模型如何提交任务、获取结果；④ 理解 future、线程池与 NPU 的关系；⑤ 分析输入尺寸、模型文件和后处理逻辑 三模型推理时序图、RKNN 依赖清单
Day 8：检测融合、拼图、编码和推流 ① 阅读 detection_fusion_manager.cpp；② 阅读 combineImage()；③ 阅读 streaming_manager.cpp、mpp_encoder.cpp；④ 理解画框、拼图和 RTMP 推流；⑤ 阅读 runtime_monitor.cpp，分析监控指标 完整系统架构图、输出流程图
Day 9：移植技术分析 ① 学习 ARM64 和交叉编译原理；② 学习 ELF、动态库、ABI、sysroot；③ 检查现有 FFmpeg、OpenCV、MPP、RKNN 库；④ 找出源码中的平台相关接口；⑤ 记录 RV1126B SDK 到货后必须核对的内容 移植依赖表、风险清单、SDK 检查表
Day 10：全面复盘和上板准备 ① 从 main() 重新梳理程序启动到退出；② 复习 C++、线程、网络、I/O 和 CMake；③ 整理原项目配置及运行流程；④ 制定逐项功能回归测试；⑤ 准备交叉编译和硬件调试所需的命令清单 完整项目分析文档、原功能测试清单、上板执行手册

第 10 天必须达到的水平

这天我们进行第一次比较完整的项目检查。

无板阶段验收标准

能完整画出原项目的模块与数据流

能讲清 main() 的启动、运行和退出流程

能解释三模型并发推理与检测融合

能解释视频输入、解码、拼图、编码和 RTMP 推流

能独立编写线程、锁、条件变量和 TCP 小程序

能使用 g++、CMake 和 GDB

能够指出源码中依赖具体 Rockchip SDK 的部分

整理完成 RV1126B 平台的移植风险及功能回归清单

已完成

0/8

第 10 天结束，我们要做到：虽然还没有板子和 SDK，但已经理解原项目全部主要功能，并知道移植需要验证哪些接口。

三、Day 11～15：开发板和 SDK 到手后怎么安排？

注意，这个阶段只有 5 天，时间非常有限。

因此我会优先验证原项目的依赖和运行通路，而不是修改原有算法。

Day 11：RV1126B 系统启动 + SDK 环境

学习重点： Bootloader、Kernel、RootFS、串口调试、交叉编译。

实操目标： 检查电源和串口电平，启动开发板；识别 SDK 目录、工具链、内核版本及系统镜像；运行一个自己交叉编译的 ARM64 程序。

验收： 能登录开发板，运行交叉编译的 Hello World，获得系统版本和工具链记录。

Day 12：验证原项目依赖库与编译环境

学习重点： 动态库、链接、MPP、RKNN Runtime、ARM64 ABI。

实操目标： 对照原项目 CMake 检查 SDK 中的 FFmpeg、OpenCV、MPP、RKNN；优先运行 SDK 对应样例；在独立移植分支上尝试编译原项目，记录缺少或不兼容的接口。

验收： 确认原项目关键库的兼容情况，尽可能完成原项目 ARM64 编译；不能编译则保留具体错误及解决清单。

Day 13：SC530AI 单摄与双摄采集

学习重点： I2C、MIPI-CSI、ISP、V4L2、摄像头缓冲。

实操目标： 先让第一颗 SC530AI 出图，检查视频节点及采集格式；再验证第二颗，最后尝试同时采集两路视频。

验收： 至少争取单摄采集成功；理想情况是双摄都能稳定出图，并保存原始帧和日志。

Day 14：原项目平台适配与功能联调

学习重点： 模块接口、资源管理、兼容层、编解码与推理。

实操目标： 优先尝试原程序使用本地视频完成解码、三模型推理、结果融合、拼图和推流；再将 SC530AI 采集接入原有视频输入流程。

保留原有文件/RTSP 输入与三个模型，不删除功能。只有底层平台不兼容的接口才需要适配。

验收： 以能够真实跑通的模块为准记录状态；条件顺利时实现摄像头输入到原有处理和输出链路的联调。

Day 15：功能回归、稳定性测试与项目总结

学习重点： GDB、日志、资源监控、性能分析、面试表达。

实操目标： 验证原功能是否保留；测试多路输入、三模型推理、检测框、拼图、推流、监控和退出逻辑；记录 CPU、内存、FPS 及运行错误。

验收： 形成项目移植报告，明确已通过、未通过和未验证的功能，保留可展示成果并整理简历内容。

需要明确：最后 5 天是集中上板移植的时间窗口，不是保证全部功能成功移植的期限。 如果 SDK 的 RKNN 版本、MPP API 或双摄驱动存在较大差异，完整移植可能需要额外时间，但我们不会为了赶进度而删掉原有功能。

四、怎样确保原项目功能没有变化？

移植之前必须建立一份功能对照表。移植完成后逐项验证，不能只以“程序能启动”作为成功标准。

测试功能 原项目行为 RV1126B 上的验收
视频输入 支持 1～6 路配置 保留原输入模式与数量配置能力
摄像头接入 原项目未直接使用 SC530AI 增加平台输入适配，不破坏已有输入
三模型推理 人员、头盔、打电话 三个模型均能正确运行
检测融合 融合多模型检测结果 输出类别、坐标与原逻辑一致
多路拼图 根据输入路数进行布局 布局与绘制逻辑保持一致
视频输出 编码并通过 RTMP 推流 能在播放端接收视频
性能监控 原有运行指标采集 保留监控功能
异常处理 现有错误处理和退出流程 保留并确保平台资源安全释放

原程序配置的目标输出帧率为 24 FPS；RV1126B 上能否达到这一性能，还需要实际上板测试。功能一致不等于性能一定相同。

我们的移植原则是：软件业务逻辑尽量保持不动，把修改集中在不同芯片平台确实需要适配的地方，比如 SDK 库、硬件接口、模型运行环境与构建配置。

五、每天固定的学习时间

根据你的 C++ 基础，我建议每天约 7 小时有效学习：

时间 前 10 天 后 5 天
09:00–10:30 C++ / Linux 基础 SDK 文档与问题分析
10:40–12:00 原项目源码阅读 板端环境或模块调试
13:30–15:30 C++ 独立编程练习 编译、部署和联调
15:40–17:00 原项目流程分析 问题定位、测试
19:00–20:00 面试题、笔记 调试复盘、记录

你不需要第一天就全部理解，只需要按当天目标逐步推进。

六、接下来我们的学习方式

从 Day 1 开始，我会对每一天采用相同的教学流程：

  1. 先讲解当天的 Linux/C++ 核心知识，并给出简单例子
  2. 安排可以在 Ubuntu 虚拟机运行的编程练习
  3. 指出当天应该阅读的原项目文件、函数和重点代码
  4. 对照项目解释知识点在真实工程中的作用
  5. 提供当天验收任务及面试测试题，并根据你的实际答案查漏补缺

还有两条执行规则：

第一，学习用的小 Demo 与原项目代码分开。 Demo 可以模拟线程池、视频输入和数据缓存，用于理解知识，但不代替原项目，也不会擅自删减原项目功能。

第二，前 10 天不依赖 SDK。 我们只做能实际验证的 C++、Linux 和源码分析；不猜测 SDK 中一定存在什么接口，更不会提前假定原项目在 RV1126B 上能够直接编译运行。

现在可以正式开始

你的整体安排已经确定。接下来的 Day 1 将从 Linux 编译环境、C++ 指针与引用、STL 基础、原项目 CMake 和入口代码开始。

等你完成当天任务并提交结果，我再根据掌握情况安排 Day 2。

最终目标仍然是：15 天内尽可能掌握 Linux 应用开发的实习核心知识，并为不删减原有功能的 RV1126B 项目移植做好准备和实际验证。
